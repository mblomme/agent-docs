# Implement Domain

## Goal

Implement all aggregates, entities, value objects, and domain services in the provided scope, as documented in `/spec/product/domain`. Wire the existing DSL adapters to the implemented domain components so the existing domain acceptance scenarios pass without changing their features, bindings, contracts, or assertions.

Follow the target project's topology, technology, and applicable tactical domain-pattern skills. Keep business behavior in the domain layer, not in test adapters.

This skill is technology-agnostic. Use a technology-specific companion skill when available to handle framework setup, syntax, and conventions.

## Prerequisites and Scope

- Read `/spec/product/domain` and any explicitly referenced product specifications.
- Treat the specification as the source of truth for required behavior. Do not invent business rules or externally observable domain events. Add implementation-supporting events only when consistent with the specification and project conventions.
- Restrict implementation to the requested scope. If none is provided, implement the entire documented domain layer and nothing less.
- Locate the acceptance artifacts generated by `build-acceptance-tests-domain` in the target repository’s domain test area. Reuse its selected technology, framework, and artifact layout.
- Inspect the existing project structure and applicable domain-pattern skills before choosing implementation locations.
- If required acceptance artifacts are missing, report the gap and request the acceptance-test authoring workflow. Do not generate or modify them under this skill.

## Ownership and Allowed Changes

Treat acceptance features/scenarios, step bindings, DSL contracts, and shared scenario-context semantics as read-only. Resolve their actual paths and file extensions from the acceptance-test workflow and repository conventions.

Do not edit other existing test cases, assertions, expected values, scenario tags, bindings, or test-discovery configuration. Do not manually generate or edit framework-generated test files.

Allow only these changes:

1. Create or modify domain implementation files in the existing domain project and its domain-owned folders.
2. Implement the existing DSL adapters without changing existing interface contracts or method signatures. Add private fields, private helpers, and necessary imports to support real domain instances and scenario state.
3. Modify the existing scenario dependency registration only when necessary to register adapters or their scenario-scoped dependencies. Preserve existing bindings and shared context semantics.
4. Make narrowly scoped project-reference changes only if required for adapters to reference the domain project. Do not change package versions, test filters, test-generation settings, or unrelated build configuration to obtain passing tests.

Do not modify specifications, application or infrastructure behavior, or unrelated `src/**`  files. 

## Workflow

### 1. Establish Traceability and a Baseline

Build a traceability table containing:

- Specification file and section anchor or rule ID.
- Required behavior, including boundaries and failure cases.
- Existing feature, rule, scenario, and relevant Examples rows.
- DSL contract methods involved.
- Domain components and methods implementing the behavior.
- Verification result or blocker.

Keep the table in the final report or an existing authorized tracking location. Do not modify specifications to record progress.

Inspect features, bindings, contracts, adapter skeletons, shared context, and dependency registration. Use each skeleton's explicit not-implemented failure and specification link to identify its intended behavior.

Run a baseline build and test execution. Record pre-existing failures separately from acceptance scenarios intentionally failing with specification-linked not-implemented failures.

### 2. Implement the full domain scope first.

- Use the specification's Ubiquitous Language from the spec folder and the project's domain conventions.
- Apply the available tactical pattern skills for aggregates, entities, value objects, domain services, and domain events.
- Enforce invariants in domain components. Do not rely on adapters to enforce business rules.
- Preserve aggregate boundaries and specified consistency requirements. Do not invent cross-aggregate orchestration or transaction semantics merely to satisfy a scenario.
- Use the project's specified failure model: exceptions, result values, or domain error states. Do not replace invariant failures with success or fabricate failure events.
- Keep domain components independent of acceptance frameworks, test runners, assertion libraries, and test DSL types.
- Implement specified behavior even when the existing scenarios do not fully cover it. Report missing acceptance coverage rather than silently narrowing scope or authoring tests.

### 3. Wire the DSL Adapters second.

Preserve the existing one-feature-to-one-DSL mapping and any existing cross-aggregate exception to that mapping.

For each adapter:

- Replace specification-linked not-implemented stubs with calls to real domain components.
- Preserve all existing public signatures and contract types. Do not expose domain types through contracts or bindings.
- Use setup methods to construct valid domain state through supported domain APIs, factories, or builders. Do not bypass invariants with reflection or direct mutation of private state.
- Use action methods to invoke the real domain behavior with the supplied parameters.
- Use inspection methods to return actual state, results, errors, or emitted events from the exercised domain components, mapped to the contract's existing types.
- Keep only test plumbing in adapters: scenario-local instance lookup, parameter conversion, domain invocation, and projection of observed values.
- Keep actors, identifiers, quantities, dates, and other inputs parameterized. Do not special-case scenario names, persona names, or Examples rows.
- Do not add assertions to adapters. All acceptance assertions remain in the existing outcome bindings.
- Do not implement a parallel domain model, duplicate business calculations, return expected constants, or use fake domain components to satisfy assertions.

Inspection results must derive from the domain operation and its resulting state. Never store an expected Gherkin value solely to return it later as an observed result.

### 4. Preserve Failure and Time Semantics

Inspect how the existing bindings and shared scenario context capture domain failures before implementing adapter exception handling.

- Capture expected domain failures only at the boundary required by the existing bindings and context contract.
- If bindings already capture failures, let the adapter propagate them. If the adapter must capture them, preserve the actual exception or error state in the existing context mechanism.
- Never catch all exceptions and turn them into expected business failures. Unexpected programming errors and remaining not-implemented failures must fail the scenario.
- Clear previous operation results or captured failures at the appropriate action boundary so a later assertion cannot pass against stale state.
- Preserve rejected-operation state semantics from the specification, including unchanged state when required.
- Reuse the scenario's existing reference anchor or frozen clock. Do not independently read the live wall clock in adapters to reinterpret dates already resolved by bindings or context.
- Keep scenario state isolated. Avoid static mutable registries, shared domain instances, and cross-scenario caches. Share dependencies within a scenario where multiple adapters collaborate.

### 5. Verify Without Weakening Tests

Run the repository's build, compilation, or load checks and test commands against the relevant projects, using the acceptance workflow's technology-specific guidance. Run targeted scenarios while iterating, then run the whole repository test suite before declaring completion.

- Use complete reports in the configured test runner’s supported format, rather than relying on potentially truncated console output.
- Confirm the intended test projects and all in-scope scenarios and Scenario Outline examples were discovered and executed.
- Require all in-scope scenarios to pass, with no undefined, ambiguous, pending, skipped, or ignored steps or scenarios.
- Require no remaining not-implemented stubs in in-scope adapters or domain behavior.
- Inspect the final diff to confirm protected acceptance artifacts remain unchanged and no test suppression, weakened assertions, or expected-value shortcuts were introduced.
- Reconcile the traceability table with the specification, acceptance coverage, implementation, and actual test results.

Do not treat a successful command exit code or zero discovered tests as proof of completion.

## Contradictions and Blockers

If a feature, binding, contract, or shared context contradicts the specification or cannot express its required behavior:

1. Identify the exact specification section and conflicting artifact.
2. Explain the discrepancy and the smallest required correction.
3. Do not edit the protected artifact or distort the domain implementation to accommodate it.
4. Continue independent, unblocked work and report the affected scope as blocked.

Likewise, report missing bindings, missing coverage, incompatible contract types, or necessary shared-context changes to the acceptance-test author. Do not silently invoke or perform acceptance-test authoring.

If the build or test environment is unavailable, report what could not be verified. Never claim a clean build or passing tests without executing them.

## Done

Declare completion only when:

- Every in-scope specification rule is implemented and traced to its domain components and existing acceptance coverage.
- The domain implementation follows applicable tactical pattern skills and project conventions.
- Adapters invoke real domain behavior and expose actual observations; assertions remain exclusively in the protected `[Then]` bindings.
- Protected acceptance artifacts and existing test expectations are unchanged.
- The build succeeds with zero compilation errors.
- All in-scope acceptance scenarios and examples execute and pass without suppression.
- The whole repository test suite passes, with complete reports checked.
- No specification contradictions, missing coverage, or verification blockers remain.

Finish with a concise report of implemented scope, changed files, the traceability table, build and test commands, executed/passed/failed/skipped totals, report locations, and any blockers. If any completion condition is unmet, report partial completion rather than declaring success.
